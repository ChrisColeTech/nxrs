## Built

Implemented the six paths in the file table. This is diagnostic harness enforcement, not a correction of
the MKW GPU fault. Pre-existing harness telemetry/provenance/capture code is preserved.

- `gpu_stop.py` fixes the shared latch at repository `build/GPU-STOP.json`. `NXRS_GPU_STOP_PATH` adds
  optional ambient/per-run paths; neither can replace or disable the shared path. All configured stops apply.
- `run_game.run()` checks before platform/GPU queries, immediately before writing a claim, and immediately
  before `Popen` after any claim wait. A pending, malformed, unreadable or valid stop marker refuses clearly.
  A `stopped=false` document is invalid, not a resumption override. No clearing/recovery command exists.
- Shared seed retains the exact HARNESS3 run/result fields and source paths. The original
  `build/HARNESS3/GPU-STOP.json` and result were only read, never modified or removed.
- Exit 71, in-run display resets and late resets append observations with run/log/executable/provenance
  paths, lane/PID, start/observation times and available exit/reset evidence. Exit 71 stops handover even
  if Windows has not logged a reset. Separate observations of one fault are retained rather than deduplicated.
- Storage keeps an ordered `faults` history, preserving the first observation. An exclusively created,
  flushed `.pending` journal precedes read/modify/atomic-replace of the JSON history. Failed/interrupted
  writes leave that journal blocking; optional-path failure does not prevent trying/persisting the shared path.
  A completely failed write also poisons subsequent checks in the current interpreter.
- Latch errors are accumulated while stopping/reaping the actual child (or monitored successor), included
  in the attempted summary as `gpu_stop_errors`, reported, and raised as `PersistenceError`. Final fault
  persistence precedes claim release. Original child waits are bounded; unexpected postlaunch exceptions
  also stop/reap the child. Reset diagnostic failure cannot skip the kill. PID-helper failure falls back
  to the original `Popen` handle during cleanup. `CURRENT` is reset after successful cleanup.
- `play_scenario.py` remains unchanged: its existing `finally` still restores saves after the runner raises.

## Unproven

- All 30 regressions await lead execution; syntax/import success is not behavioral acceptance.
- GPU/device-loss cause and correction are unproven. HARNESS3 and shared GPU stops remain active.
- The protocol requires one GPU workload. A journal serializes history updates by refusing a competing
  writer; it does not merge simultaneous failed-writer events or provide an OS-wide atomic launch mutex.
  `NXRS_CONCURRENT=1` still checks every stop, but parallel GPU work remains outside this protocol. External
  launches/marker mutation racing the final check are not atomically excluded.
- Total storage denial cannot guarantee a durable stop across interpreter restart. It is an explicit error,
  and the current interpreter refuses retries. A partial/failed journal remains blocking without auto-repair.
- A handed-over successor is tracked only by PID, not an owned process handle/exit status. Its display resets
  are persisted and it is stopped by PID; successor-only exit 71 without an observable reset remains unknown.
- If the OS denies termination or reaping, cleanup raises and retains the claim. The unchanged scenario
  `finally` cannot guarantee safe restoration against an unkillable process; successful termination is a
  precondition. Current mocks verify successful stop/reap and PID-helper failure with root-handle fallback.
- Existing NVIDIA event-153 detection and its query-error semantics are unchanged. Scenario daemon-thread
  cancellation and alternate tools that never call this generic runner are outside this patch.
